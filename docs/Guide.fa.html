راهنمای طاها کریتور برای Railway

نسخهٔ بازسازی: 6.0-railway — راه‌اندازی تازه، با حفظ موتور قدیمی دکمه‌سازی و بازسازی لایهٔ اجرا و مدیریت اصلی.

این بسته هنوز روی حساب واقعی Railway و با توکن‌های واقعی تو دیپلوی نشده است. وضعیت دقیق آزمون‌ها در docs/VALIDATION.fa.md نوشته شده. «وجود قابلیت در سورس» با «آزموده‌شدن تمام حالت‌های آن در تلگرام» فرق دارد؛ این بسته ادعای بی‌نقص‌بودن همهٔ مسیرهای سورس قدیمی را ندارد.

۱. دقیقاً چند ربات داریم؟

بخش در نسخهٔ اصلی کارش چیست؟ چه کسی استفاده می‌کند؟
ربات اصلی، یا ربات‌ساز Pedar.php ثبت توکن ربات تازه، سکه، دعوت، فهرست ربات‌ها، فروشگاه و مدیریت مالکیت تو و کاربرانی که اجازه بدهی
ربات مدیریت مرکزی bot.php مدیریت کاربران و سکهٔ ربات‌ساز، آمار کل، نسخه‌ها و ربات‌ها فقط OWNER_ID
ربات فرزند نسخه‌ای از Haji.php رباتی که کاربر می‌سازد؛ پنل دکمه‌سازی و تنظیمات خودش را دارد مالک همان ربات، ادمین‌هایش و کاربرانش

پس برای شروع دو توکن جدا لازم داری. برای تست ساخت ربات، یک توکن سوم هم از BotFather می‌گیری. لازم نیست برای هر ربات در Railway سرویس جدید بسازی. یک سرویس برنامه + یک MySQL، همراه فضای دائمی برنامه، میزبان همهٔ آن‌ها می‌شوند.

توکن هر ربات مثل رمز آن است. شناسهٔ عددی تو با یوزرنیم @... فرق دارد. API ID، API Hash، شماره تلفن و سشن اکانت تلگرام لازم نیست؛ این پروژه Bot API است.

۲. قبل از شروع

  • حساب GitHub و دسترسی به Railway لازم است.
  • توکن‌های داخل ZIP قدیمی را استفاده نکن. اگر متعلق به تو هستند، در BotFather آن‌ها را تعویض کن؛ در سورس به‌صورت آشکار وجود داشتند.
  • این بسته دیتابیس کاربران قبلی را ندارد. کد به‌تنهایی کاربران، موجودی‌ها و تنظیمات هاست قدیمی را منتقل نمی‌کند. برای نصب تازه از MySQL خالی استفاده کن.
  • هزینه و ظرفیت Railway به پلن حساب خودت بستگی دارد. این پروژه اجرای رایگان دائمی را تضمین نمی‌کند. برای هر دو سرویس و Volume بودجه تعیین کن.

۳. ساخت ربات‌ها در تلگرام

  1. ربات رسمی و تأییدشدهٔ @BotFather را باز کن.
  2. /newbot را بفرست؛ نام نمایشی دلخواه و سپس یوزرنیم آزاد بده که به bot ختم شود.
  3. اولین توکن را برای ربات‌ساز نگه دار: CREATOR_TOKEN.
  4. دوباره /newbot؛ ربات دوم برای مدیریت مرکزی: MANAGER_TOKEN.
  5. ربات سوم را برای تست بساز و توکنش را فعلاً نگه دار؛ آن را در Variables دو ربات اصلی وارد نکن.
  6. هر دو ربات اصلی را باز کن و Start بزن. قبل از اجرا جواب ندادنشان طبیعی است.

شناسهٔ عددی خودم را از کجا بگیرم؟

به ربات مدیریت یک پیام بفرست. قبل از راه‌اندازی، در مرورگر آدرس زیر را با توکن همان ربات باز کن:

https://api.telegram.org/botYOUR_MANAGER_TOKEN/getUpdates

در پاسخ، بخش message سپس from سپس id شناسهٔ توست. آن عدد را برای OWNER_ID بردار؛ عدد موجود در chat.id فقط در گفت‌وگوی خصوصی خودت همین است. این آدرس توکن دارد؛ آن را به کسی نده و از اسکرین‌شاتش توکن را پاک کن. بعد از نصب، /id در ربات مدیریت هم شناسه را نشان می‌دهد.

اگر result خالی است، یک پیام تازه به ربات بده و صفحه را تازه کن. اگر خطای فعال‌بودن webhook دیدی، از یک ربات مدیریتی تازه استفاده کن تا ربات دیگری را ناخواسته قطع نکنی.

۴. رساندن سورس به GitHub

در مخزن باید خودِ Dockerfile، railway.json و پوشه‌های app، bin، public و tests دیده شوند. آپلود تنها فایل ZIP کافی نیست. پوشهٔ اضافه دور پروژه هم نگذار؛ Dockerfile باید در ریشه باشد.

اگر کامپیوتر داری

ZIP را استخراج کن. در GitHub یک مخزن خصوصی تازه بساز، Add file → Upload files را بزن و فایل‌ها و پوشه‌های استخراج‌شده را با ساختارشان منتقل و Commit کن. مطمئن شو پوشهٔ .github هم منتقل شده تا آزمون خودکار اجرا شود.

اگر فقط گوشی داری

می‌توانی از Codespaces در مرورگر با حالت Desktop site استفاده کنی. پردازش آن روی سرور انجام می‌شود.

  1. در GitHub یک مخزن خصوصی مثل taha-creator-railway بساز؛ گزینهٔ ساخت README را روشن کن تا مخزن یک commit داشته باشد.
  2. Code → Codespaces → Create codespace on main را بزن. در صورت تفاوت رابط، صفحهٔ https://github.com/codespaces/new را باز و مخزن خودت را انتخاب کن.
  3. وقتی محیط ویرایشگر باز شد، در Explorer روی فضای خالی کلیک راست/لمس طولانی کن و Upload را بزن؛ فایل ZIP بازسازی‌شده را بارگذاری کن.
  4. Terminal → New Terminal را باز کن. اگر نام فایل دانلودشده فرق دارد، آن را دقیقاً به TAHA-CREATOR-Railway.zip تغییر بده. سپس این دستورها را داخل مخزن تازهٔ خودت اجرا کن:
unzip -o TAHA-CREATOR-Railway.zip
rm TAHA-CREATOR-Railway.zip
git add app bin public tests docs tools .github Dockerfile railway.json README.fa.md .env.example .gitignore .dockerignore
git commit -m "Add Railway rebuild"
git push
  1. به صفحهٔ مخزن برگرد؛ اکنون باید Dockerfile را کنار فایل‌ها ببینی. در تب Actions نتیجهٔ Validate را ببین. اگر قرمز است، جزئیات همان خطا را بررسی کن و فعلاً سرویس را عمومی نکن.
  2. بعد از کار Codespace را Stop کن تا بی‌دلیل روشن نماند. سهمیه و هزینهٔ Codespaces را در حساب خودت بررسی کن.

توکن‌ها را داخل GitHub، README یا فایل PHP نگذار. .env.example صرفاً نمونه است و به‌صورت خودکار توسط Railway خوانده نمی‌شود.

۵. ساخت پروژهٔ Railway

  1. در Railway یک پروژهٔ تازه بساز.
  2. از New / Create، یک دیتابیس MySQL اضافه کن؛ نه PostgreSQL. نام سرویس را MySQL بگذار تا نمونهٔ متغیرهای پایین بدون تغییر کار کند.
  3. صبر کن MySQL آماده شود. Volume دیتابیس را حذف نکن.
  4. داخل همین پروژه، سرویس دیگری از GitHub Repo ایجاد و مخزن سورس را انتخاب کن.
  5. Railway باید Dockerfile را تشخیص بدهد. Build Command و Start Command سفارشی لازم نیست؛ این دو را خالی بگذار.
  6. برای سرویس برنامه یک Volume بساز و Mount path را دقیقاً /data بگذار. این Volume جدا از Volume خود MySQL است. فایل‌های ربات‌های فرزند و وضعیت‌های فایل‌محور آنجا می‌مانند.
  7. تعداد Replica را ۱ نگه دار. این نسخه صف تک‌پردازشگر دارد و برای چند Replica طراحی نشده است.
  8. اگر گزینهٔ Serverless / Sleep روشن است، آن را برای این سرویس خاموش کن تا پردازش صف متوقف نشود.

در نخستین تلاش، قبل از تنظیم متغیرها خطای Missing variable طبیعی است؛ بعد از تکمیل تنظیمات Redeploy می‌کنی.

۶. متغیرهای ضروری

روی سرویس برنامه برو، نه سرویس MySQL. تب Variables را باز کن و این موارد را وارد کن. در مقدار توکن و شناسه، علامت نقل‌قول نگذار.

نام مقدار
CREATOR_TOKEN توکن ربات اول
MANAGER_TOKEN توکن ربات دوم
OWNER_ID شناسهٔ عددی خودت
APP_SECRET یک رشتهٔ تصادفی حداقل ۳۲ کاراکتری؛ پیشنهاد ۶۴ کاراکتر
MYSQLHOST ${{MySQL.MYSQLHOST}}
MYSQLPORT ${{MySQL.MYSQLPORT}}
MYSQLUSER ${{MySQL.MYSQLUSER}}
MYSQLPASSWORD ${{MySQL.MYSQLPASSWORD}}
MYSQLDATABASE ${{MySQL.MYSQLDATABASE}}
DATA_DIR /data
PUBLIC_CREATOR false برای شروع
SUPPORT_USERNAME یوزرنیم پشتیبانی خودت بدون @

اگر نام سرویس دیتابیس را چیز دیگری گذاشتی، در پنج مقدار ${{...}}، MySQL را با نام دقیق همان سرویس عوض کن. این‌ها Reference Variable هستند، نه مشخصات دیتابیس قدیمی.

برای ساخت APP_SECRET در Terminal همان Codespaces:

openssl rand -hex 32

خروجی را کپی و در Variables وارد کن. آن را برای این پروژه ثابت نگه دار؛ تغییرش وبهوک‌ها را دوباره ثبت می‌کند.

۷. دامنه و اتصال خودکار تلگرام

  1. Settings سرویس برنامه → Networking / Public Networking → Generate Domain.
  2. اگر پورت خواست، 8080 بده و متغیر PORT=8080 هم در سرویس برنامه بگذار. اگر از PORT خودکار Railway استفاده می‌کنی، Target port باید با همان برابر باشد.
  3. دامنهٔ تولیدشده را در متغیر BASE_URL با https:// و بدون / آخر قرار بده:
https://your-project.up.railway.app
  1. Apply changes / Deploy یا Redeploy را بزن.
  2. در Logs باید پیام initialized و سپس Webhooks configured. ظاهر شود.
  3. آدرس زیر را باز کن:
https://your-project.up.railway.app/healthz

پاسخ باید ok: true داشته باشد. این بررسی اتصال دیتابیس و زنده‌بودن پردازشگر را می‌سنجد؛ به‌تنهایی تضمین نمی‌کند همهٔ قابلیت‌های تلگرام درست کار می‌کنند.

نیازی به ساخت لینک setWebhook دستی نیست. برنامه وبهوک دو ربات اصلی را خودش ثبت می‌کند و هنگام ثبت هر فرزند، وبهوک همان را می‌سازد. لینک‌های /bot.php و /Pedar.php را در مرورگر باز کنی، پاسخ 405 طبیعی است؛ این مسیرها پیام POST تلگرام با رمز مخصوص می‌خواهند.

۸. اولین تست واقعی

  1. در ربات مدیریت /start بفرست؛ فهرست دستورات باید بیاید.
  2. در ربات اصلی /start بفرست؛ منوی فارسی باید بیاید.
  3. در ربات مدیریت addcoin را بفرست؛ سپس شناسهٔ خودت؛ سپس 1000.
  4. در ربات اصلی /mycoin را بفرست و موجودی را ببین.
  5. /newbot را در ربات اصلی بفرست و توکن ربات سوم را بده. پیش‌فرض، ساخت ربات ۵۰۰ سکه کم می‌کند.
  6. ربات سوم را باز کن، /start و بعد /panel بفرست.
  7. «افزودن دکمه جدید🔧» را انتخاب کن. جای دکمه را از بالا/پایین تعیین کن؛ نوع «متن تکی🔰» را انتخاب کن؛ سپس نامی مثل «سلام» بده. از «ویرایش دکمه ها✂» همان دکمه را انتخاب کن، «تعیین مطلب🆕» را بزن و متن ساده بده. هر جا منوی فعلی ورودی دیگری خواست، همان را تکمیل کن.
  8. «خروج از پنل🏠» را بزن و دکمهٔ «سلام» را امتحان کن.
  9. با حساب مجاز دیگری ربات فرزند را تست کن: آن حساب نباید بتواند /panel را باز کند مگر ادمینش کرده باشی.
  10. یک بار سرویس برنامه را Redeploy کن؛ دکمه و موجودی باید باقی بمانند. این تست Volume و MySQL را هم بررسی می‌کند.

قبل از بازکردن ربات‌ساز برای دیگران، این ده مرحله و آزمون‌های انتهای راهنما را انجام بده.

برای عضویت اجباری، ربات مربوطه باید در کانال عضو و برای اطمینان از بررسی عضویت، ادمین باشد. برای انتشار آگهی یا پست در کانال، دسترسی ارسال پیام لازم است. برای حذف پیام گروه، دسترسی حذف لازم است.

تنظیم عضویت اجباری در ربات اصلی از Variables است؛ تنظیم عضویت اجباری هر ربات فرزند از پنل همان ربات انجام می‌شود.

برای امکانات Inline/اشتراک‌گذاری، در BotFather گزینهٔ /setinline را برای ربات فرزند تنظیم کن. برای پردازش پیام‌های عادی گروه، وضعیت Privacy Mode و دسترسی‌های ربات را در BotFather و گروه بررسی کن؛ در صورت نیاز /setprivacy را تنظیم و دوباره ربات را به گروه اضافه کن.

۱۱. بکاپ و به‌روزرسانی

کد در GitHub، داده‌ها در MySQL و فایل‌های ساخته‌شده در Volume هستند. بکاپ کد به‌تنهایی کافی نیست. برای MySQL و Volume برنامه، قابلیت Backup در حساب Railway را بررسی و فعال کن. قبل از حذف جدول، ریست، تغییر بزرگ یا جابه‌جایی سرویس‌ها بکاپ بگیر. حذف پروژه یا Volume می‌تواند داده‌ها را از بین ببرد.

برای به‌روزرسانی کد، تغییرات را در GitHub Commit/Push کن؛ Railway را Redeploy کن. در شروع، قالب ربات‌های ثبت‌شده بازسازی می‌شود؛ دکمه‌ها و داده‌ها از MySQL خوانده می‌شوند. متغیرها، Volume و دیتابیس را نگه دار.

فرمان update در ربات مدیریت فقط «خبر نسخه و توضیحات» ثبت می‌کند؛ کد جدید دانلود نمی‌کند. updateallbot همهٔ فایل‌های فرزند را از قالب فعلی بازسازی می‌کند. از نام نسخهٔ متفاوت با 6.0-railway فقط زمانی استفاده کن که واقعاً کد/نسخه را تغییر داده باشی.

حذف ربات در لایهٔ بازسازی‌شده، وبهوک و ثبت فعال آن را حذف می‌کند ولی جدول‌ها را برای بازیابی باقی می‌گذارد. این تفاوت عمدی با پاک‌کردن کامل قدیمی است. اگر دوباره همان ربات را با توکن معتبر ثبت کنی، داده‌های باقی‌مانده قابل استفاده‌اند. این کار ۵۰۰ سکهٔ ساخت را دوباره می‌گیرد؛ هزینه را در نظر بگیر.

۱۲. عیب‌یابی

مشکل چه چیزی را بررسی کنم؟
Missing variable متغیر روی سرویس برنامه وارد نشده یا نامش اشتباه است

محدودهٔ بررسی

ZIP اولیه ۱۴ ورودی و ۹ فایل PHP داشت؛ index.php خالی بود. جمع فایل‌های PHP حدود ۲۹٬۱۳۱ خط بود. در شرط‌های مستقیم متن، ۳۷۳ عنوان مجزا به تفکیک فایل استخراج شد: ۳۱۹ در قالب فرزند، ۳۳ در ربات اصلی و ۲۱ در ابزار مدیریت. فرمان‌های جایگزین /newbot و مانند آن و callbackها جدا در مرجع توضیح داده شده‌اند؛ این عدد شمار قابلیت‌های مستقل نیست.

بازسازی از نوع انتقال و اصلاح موتور موجود است: موتور چندبخشی Haji حفظ شده، لایهٔ اجرای Railway و مسیرهای اصلی مدیریت بازنویسی شده‌اند. این پروژه یک بازنویسی خط‌به‌خطِ کل ۲۹ هزار خط با تضمین تطابق کامل رفتار نیست.

ایرادهای مهم یافت‌شده

  1. توکن و رمز دیتابیس داخل سورس: توکن‌های ثابت و اتصال به MySQL قدیمی حذف شده‌اند. هیچ توکن قدیمی در بستهٔ خروجی قرار ندارد.

  2. ارسال توکن به کانال ثابت: بعضی مسیرهای ساخت/آپدیت توکن را به یک کانال ثابت و حتی با یک توکن گزارش‌گیر جدا می‌فرستادند. درخواست‌های گزارش‌گیر قدیمی حذف و نمایش توکن در متن پیام ماسک شده است.

  3. دسترسی ویژهٔ شناسهٔ قدیمی: Haji مالک ربات را برای یک شناسهٔ ثابت بازنویسی می‌کرد. این مسیر حذف شد. ابزار مدیریتی اولیه نیز کنترل دسترسی سراسری کافی نداشت؛ در نسخهٔ جدید فقط مالک اصلی در خصوصی وارد می‌شود.

  4. دامنهٔ ثابت و تشخیص IP: دامنهٔ هاست قدیمی و بررسی مستقیم REMOTE_ADDR با پروکسی Railway سازگار نبودند. وبهوک جدید از BASE_URL و هدر secret_token استفاده می‌کند.

  5. دکمهٔ ساخت نامنطبق: متن کیبورد «غیرفعال» داشت ولی handler منتظر «خاموش» بود. عنوان یکسان و مسیر جدید ساخت اضافه شد.

  6. پاک‌کردن رشته‌ها از توکن: حذف واژه‌هایی مثل file و php می‌توانست توکن معتبر را خراب کند. این دستکاری کنار گذاشته شد؛ اعتبار با getMe سنجیده می‌شود.

  7. SQL و شناسه‌های بزرگ: جدول‌های نصب تازه utf8mb4 و شناسه‌های BIGINT دارند. بسیاری از مقدارهای SQL escape شده‌اند و ۲۸۵ فراخوانی insert در موتور فرزند به آرایهٔ پارامتر تبدیل شده است. این به‌معنی گواهی امنیت کامل تمام مسیرهای موتور قدیمی نیست.

  8. بازنویسی ناقص مالکیت بازار: انتقال مالکیت صرفاً با تغییر متن فایل در برابر Redeploy پایدار نبود. مسیر خرید جدید creatorid را هم در دیتابیس مرجع تغییر می‌دهد.

  9. تکرار webhook و پایان زودرس درخواست: ورودی ابتدا در صف MySQL ثبت می‌شود. کلید ترکیبی route/update_id تکرار یک آپدیت را حذف می‌کند. فایل هر ربات در پردازش مستقل اجرا می‌شود؛ پیام‌های طولانی مستقیماً در درخواست HTTP اجرا نمی‌شوند.

  10. ناسازگاری‌های PHP 8: شمارش null، نتایج نامعتبر دیتابیس، نام کلاس CURLFile پس از namespace، چند messageid بدون علامت دلار، getKeygroup بدون پرانتز و فونت 95px از موارد اصلاح‌شده‌اند.

  11. ابزار به‌روزرسانی جمعی گمشده: فرمان قدیمی فقط update.json می‌نوشت؛ پردازشگرش در ZIP نبود. مدیریت جدید خودش قالب ثبت‌شده‌ها را بازسازی می‌کند.

  12. پنل و ذخیرهٔ محتوا: فراخوانی بدون ورودی getEditer در /panel و escape دوبارهٔ JSON در ذخیرهٔ مطلب و پاسخ خودکار اصلاح شدند؛ دکمهٔ متن ساده با کاربر آزمایشی دوم بازپخش شد.

تفاوت‌های عمدی

  • دسترسی عمومی ربات‌ساز ابتدا بسته است و با PUBLIC_CREATOR باز می‌شود.
  • حذف در مدیریت مرکزی و منوی اصلی بازسازی‌شده توقف و حذف از ثبت فعال است؛ جداول برای بازیابی می‌مانند. بعضی ابزارهای قدیمی داخل فرزند همچنان پاکسازی سخت دارند.
  • فرمان‌های debug مدیریت مثل getstep حالا کاربر هدف می‌گیرند و فقط به مرحلهٔ خود ادمین محدود نیستند.
  • دستورات مخرب مدیریت مرحلهٔ تأیید دارند. deletetable محتوای جدول را پاک می‌کند، نه ساختار جدول را.
  • توکن در پاسخ، اعلان و گزارش نمایش داده نمی‌شود.
  • درخواست‌های عمومی به شبکهٔ خصوصی و پورت‌های غیر HTTP(S) پذیرفته نمی‌شوند؛ APIهای نیازمند redirect ممکن است به URL نهایی نیاز داشته باشند.
  • اجرای PHP بیرونی پیش‌فرض خاموش است. موفقیت سرویس بیرونی تضمین نشده است.
  • گزینهٔ اسلات در خروجی قابل اجرا نیست؛ انیمیشن‌های معمولی توپ و تاس مستقل از شرط‌بندی هستند.
  • نسخهٔ جدید یک worker و یک Replica دارد؛ زمان‌سنج‌های قدیمی حذف محتوا همچنان ممکن است به دریافت آپدیت بعدی وابسته باشند.

محدودیت‌های باقی‌مانده و مواردی که «وجود نداشت»

  • پرداخت بانکی، پرداخت خودکار خرید سکه، صدور خودکار حساب BotFather، یا مدیریت اکانت شخصی تلگرام وجود ندارد.
  • فقط با داشتن سورس نمی‌شود کاربران و سکه‌های دیتابیس قدیمی را بازیابی کرد.
  • نمودار روزانهٔ اولیه کلید روزِ ماه دارد؛ گزارش تحلیلی صحیح چندماهه نیست.
  • قالب قدیمی در بعضی مسیرها نام و متن را ساده‌سازی می‌کند؛ همهٔ جزئیات قالب‌بندی و ترکیب‌های زبان الگو هنوز تست زنده نشده‌اند.
  • crash وسط یک عملیات قدیمی می‌تواند نتیجهٔ نامطمئن داشته باشد. چنین پیام‌هایی خودکار دوباره اجرا نمی‌شوند تا امتیاز یا عملیات تکرار نشود؛ در /status با failed/uncertain مشخص‌اند.
  • دیتابیس قدیمیِ واقعی و کار با نسخه‌های ناشناختهٔ آن آزمایش نشده است؛ راهنما برای نصب تازه است.
  • بستهٔ Docker، اتصالات واقعی Railway، سرعت تحت بار و تحویل پیام واقعی تلگرام باید در محیط خودت آزموده شوند. گزارش VALIDATION دقیقاً می‌گوید چه آزمون‌هایی اینجا اجرا شده‌اند.

دکمه‌های شیشه‌ای فروشگاه

کدهای taiid-+-... و rad-+-... به تأیید/رد آگهی مربوط‌اند و فقط مدیر بررسی مجاز است. like-+-... و dislike-+-... رأی آگهی، mahsol-+-... نمایش محصول، و buy-... خرید ربات با سکه است. این‌ها callback داخلی‌اند؛ به‌صورت پیام عادی ارسال نمی‌شوند. نسخهٔ جدید قیمت و مالک آگهی را در دیتابیس کنترل می‌کند و متن callback به‌تنهایی مرجع قیمت نیست.

متغیرهای متن در ربات فرزند

این نام‌ها در متن محتوا جایگزین می‌شوند؛ دستورات BotFather نیستند. جایگذاری‌های قدیمی ساده و حساس به متن هستند. ابتدا یک متن آزمایشی کوتاه بساز.

این خانواده‌ها بخشی از زبان الگوی اختصاصی سورس‌اند، نه PHP استاندارد. نحوهای ترکیبی و همهٔ حالت‌های آن‌ها آزموده نشده‌اند؛ برای استفادهٔ روزمره گزینه‌های منویی مناسب‌ترند. در نسخهٔ بازسازی‌شده خروجی PHP روی سرور ربات اجرا نمی‌شود.

نتیجهٔ آزمون‌ها

گزارش آزمون نسخهٔ 6.0-railway

تاریخ بررسی: ۲۰۲۶-۰۹-۲۲. آزمون‌ها با توکن ساختگی و جایگزین محلی ارتباط تلگرام اجرا شدند؛ هیچ پیام واقعی ارسال نشد.

آزمون نتیجه و دامنه
PHP 8.3 بررسی نحوی ۱۴ فایل PHP موفق
tests/unit.php موفق؛ رمز مجزای webhook، مسیر فرزند، رد شناسهٔ SQL نامعتبر، ماسک توکن، حذف ردیف خالی کیبورد، نوشتن اتمیک و جلوگیری از نوشتن بیرون DATA_DIR
tests/integration.php موفق با MariaDB 10.11 محلی؛ schema، ساخت ربات، کسر دقیق ۵۰۰ سکه، رد ثبت تکراری بدون کسر دوباره، ذخیرهٔ متن فارسی و کوتیشن، حذف آپدیت تکراری، رد مدیر غیرمجاز و حذف/بازپرداخت
موتور قدیمی فرزند اجرای /start، /panel، انتخاب محل و نوع دکمه، ثبت نام، ورود به ویرایش و ثبت مطلب موفق
دریافت محتوای دکمه کاربر آزمایشی دوم دکمه را انتخاب کرد و درخواست sendMessage با همان متن ثبت‌شده تولید شد
دسترسی پنل فرزند کاربر غیرمالک با /panel وارد پنل نشد
ربات‌ساز /start منوی اصلی را تولید کرد

این آزمون‌ها دو اشکال اجرایی دیگر را مشخص کردند: فراخوانی بدون ورودی getEditer در /panel و escape دوبارهٔ JSON هنگام ذخیرهٔ محتوا. هر دو اصلاح و مسیر مربوط دوباره اجرا شد.

آنچه اینجا آزموده نشده

  • ساخت نهایی تصویر Docker و اجرای Apache داخل آن؛ ابزار Docker در این محیط اجرا نشد.
  • اجرای workflow روی GitHub و MySQL 8.4 واقعی؛ فایل workflow برای این آزمون آماده است، اما نتیجهٔ سبز آن هنوز گزارش نشده است.
  • اتصال واقعی Railway، ثبت webhook با توکن واقعی، تحویل واقعی رسانه و پیام، پایداری Volume بعد از Redeploy و بازیابی بکاپ.
  • همهٔ ۳۷۳ عنوان منو/فرمان، تمام ترکیب‌های فرم و قفل، خرید و انتقال، گروه، Inline، سرویس PHP بیرونی، RSS و بار چندکاربره.

بنابراین نسخه برای راه‌اندازی آزمایشی آماده شده، اما تأیید نهایی استفادهٔ عمومی نیازمند مراحل پذیرش README و AUDIT است. این گزارش گواهی امنیت یا تضمین بی‌نقصی نیست.

اجرای مجدد آزمون‌ها برای توسعه‌دهنده

php tests/unit.php بدون دیتابیس اجرا می‌شود. آزمون integration به دیتابیس آزمایشی جدا، متغیرهای MYSQL، OWNER_ID، APP_SECRET، BASE_URL، DATA_DIR و TC_TEST_DATABASE=true نیاز دارد. آن را روی دیتابیس کاربران واقعی اجرا نکن، چون دادهٔ تست ایجاد و تغییر می‌دهد. GitHub Actions این متغیرها و دیتابیس جدا را فراهم می‌کند.

tests/legacy_case.php ابزار بازپخش یک پیام مصنوعی است. ابتدا با ورودی setup قالب تست را می‌سازد. سپس با ورودی‌های نام مسیر، متن پیام و شناسهٔ کاربر اجرا می‌شود؛ خروجی JSON درخواست‌های تولیدشده است. این ابزار به‌تنهایی assertion همهٔ قابلیت‌ها نیست.
